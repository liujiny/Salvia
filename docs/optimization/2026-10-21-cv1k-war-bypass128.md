# CV1000: Staging Snapshot Bypass Threshold Refinement to Eliminate Multi-Part Sprite WAR Flushes

Baseline `98e3e597` (Harissa-inspired SH-3 idle spin loop fast-forwarding across scanline slices). Refinement of the staging snapshot bypass threshold in `libretro/FBNeo/src/burn/devices/epic12_gpu.h` from `w > 64 && h <= 4` to `w > 128 && h <= 4`, along with bounds hardening on candidate page accumulation (`npl[128]`), eliminating write-after-read (WAR) stall flushes triggered by multi-part boss explosion strips and bullet barrages while preserving water raster bypass.

## Why

1. **Hardware Log Diagnosis (15,001 Gameplay Frames)**:
   - Analysis of real Xbox 360 runtime logs (`cv1000-gpu-latest.log`) from the candidate image showed that Harissa idle fast-forwarding eliminated CPU spin loop churn (`drc_movll_service` calls dropped by up to 87.8%, idle time dropped by 62.8%).
   - However, during boss explosions and bullet barrages, frame time spiked up to 46.59 ms (dropping instantaneous FPS down to 30–40 FPS). The breakdown revealed:
     - `cpu_io = 23.58 ms`
     - `draw_sync = 22.88 ms`
     - `worker_wait peak = 24.02 ms`
   - The diagnostic telemetry showed `source_dependency = 188` flushes, exactly matching `war768 = 188`.
   - The 10 captured `diag_war_sample` entries uniformly showed draw commands with dimensions $w \in [71, 128]$ and $h \in [2, 4]$ sampling from staging VRAM at $(768, 0)$ or $(1280, 0)$.

2. **The Staging Bypass Threshold Defect**:
   - In `epic12_gpu.h`, line 1909 previously read:
     ```cpp
     if (sx >= 768 && sy < 4096 && w <= 512 && h <= 256 && !(w > 64 && h <= 4))
     ```
   - This bypass condition was originally intended to bypass Stage 1 full-screen water raster scanlines ($w \approx 324..352, h = 1$) so that single-pixel horizontal lines would not scatter and exhaust the snapshot shelf allocator.
   - However, because the width threshold was set to `w > 64`, multi-part boss explosion strips and bullet strips ($w \in [71, 128]$ with $h \in [2, 4]$) also matched `w > 64 && h <= 4` and were erroneously excluded from snapshotting.
   - Consequently, these strips were submitted to the GPU queue sampling directly from staging VRAM at $(768, 0)$. When the CPU immediately prepared the subsequent frame by writing to $(768, 0)$, `epic12_gpu_staging_blit` detected that the GPU was still reading from $(768, 0)$ and triggered a full synchronous GPU stall (`draw_sync` lasting up to 22.88 ms).

3. **Shelf Allocator Capacity**:
   - The snapshot shelf allocator (`w <= 128 && h <= 128`) aligns heights to multiples of 4 pixels. A strip with $w \le 128$ and $h \le 4$ occupies only a single row of height 4 within a $128 \times 128$ shelf page (accommodating up to 32 strips per page).
   - Across the 128 available snapshot pages, thousands of such strips can be packed without exhausting the atlas.
   - Raising the threshold to `w > 128 && h <= 4` allows all multi-part boss and bullet strips ($w \le 128$) to be snapshotted safely, relocating their source to snapshot VRAM ($y \ge 4096$) and completely freeing staging VRAM at $x \ge 768$ from GPU read dependencies.

## What

1. **`libretro/FBNeo/src/burn/devices/epic12_gpu.h`**:
   - Refined staging snapshot condition to:
     ```cpp
     if (sx >= 768 && sy < 4096 && w <= 512 && h <= 256 && !(w > 128 && h <= 4))
     ```
   - Expanded stack-allocated page candidate buffer from `int npl[32]` to `int npl[128]` in `epic12_gpu_submit`.
   - Added bounds check in `epic12_gpu_can_fit` to prevent overflow if `newPages` reaches 128.

2. **`libretro/FBNeo/tests/epic12_gpu/test.cpp`**:
   - Added unit test `staging_snapshot_war_prevention`:
     - Verifies that draw commands from staging VRAM ($sx = 768$) with $w = 71, h = 4$ are snapshotted out of staging page 6 into the snapshot atlas.
     - Verifies that subsequent CPU writes to page 6 do not trigger a `EPIC12_GPU_FLUSH_SOURCE_DEPENDENCY` WAR flush.
     - Verifies that full-screen rasters ($w = 320, h = 1$) remain bypassed.
