# CV1000: give the arena back the headroom the fall-through fusion consumed

Baseline for this round: `27365138` (the restored delayed-conditional
fall-through). One logical change: the arena size constant.

## Why

The console winning image of `2026-10-09-cv1k-delayed-conditional-fallthrough.md`
carried its own cost, visible in the same pause report:

| per 3,524-frame window | fusion, 20 MiB arena |
| --- | ---: |
| `drc_work_arena peak_words` | 5,239,092 (99.9% of 20 MiB) |
| `evictions` / `evicted_slots` | 4 / 5,633 |
| `rebuilds` | 64 (sampled 1-in-256) |
| frames >= 25 ms | 1 of 52 (25.55 ms) |

The fused blocks are ~40% more live code, so the working set reaches the 20 MiB
arena inside one console-length window and the sector ring starts reusing 1 MiB
sectors: 5,633 block-table slots dropped, and the guest rebuilding them through
`compile()` is the stall class this arena work exists to bound. The
pre-fusion image of the same session had 0 evictions and 0 frames at or above
25 ms.

## Change

`SH3_PPC_CACHE_BYTES` 20 MiB -> 32 MiB, which is the size the pre-ring sweep
(`2026-10-07-cv1k-block-table-size.md`) measured as the default before the
ring round chose a smaller arena to exercise sector reuse. Nothing else moves:
the sector size stays 1 MiB, the block table stays 131,072 entries, the arena
is still the same static array on Xbox (`.bss` grows by 12 MiB; the 32 MiB
default previously measured `.bss` at 0x04d6bc7c).

## Host verification

`ddpdfk` from `user-ddpdfk4-core.state`, `dips=00,07,00,00`, `render_cores=2`,
no input, `qemu-ppc -cpu g4`.

60 frames: `STATE 0cf251c3d512ddbb`, the per-frame video/audio hash file,
`native_calls` (4,725,573), `native_guest_cycles`, `interpreter_steps`,
`rebuilds` and every `drc_work_codegen` phase are byte-identical to the 20 MiB
build -- the arena size changes when code is regenerated, never what is
generated.

1800 frames, same state:

| 1800 frames | pre-fusion `958ad026` | fusion, 20 MiB | fusion, 32 MiB |
| --- | ---: | ---: | ---: |
| `native_calls` | 80,011,513 | 66,849,642 | 66,849,642 |
| `rebuilds` | 30,541 | 33,108 | **30,913** |
| arena `peak_words` | 3,718,292 (70.9%) | 5,238,984 (99.9%) | **5,333,584 (63.6%)** |
| `evictions` / `evicted_slots` | 0 / 0 | 2 / 3,234 | **0 / 0** |
| `recycles` | 0 | 0 | 0 |
| `STATE` | dff81882efc1b24a | dff81882efc1b24a | dff81882efc1b24a |

The fusion's rebuild penalty (+8.4% at 20 MiB) is gone: 30,913 against the
pre-fusion 30,541 is +1.2%, and the eviction class is back to zero for a window
as long as the console run. The peak lands at 63.6% instead of 99.9%, so a
long session has roughly 1,000 more frames before the first sector reuse.

## Limits

Host evidence only. The change cannot alter emulation (it is an allocation
size, and the equivalence above is exact), so the console question is narrower
than usual: does the eviction class show up at all in a play session, and does
the `sampled_peak_ms` outlier of the previous image return to its pre-fusion
value. No release flavor was compiled for this commit; it belongs in the same
acceptance build as the fusion it pays for.
